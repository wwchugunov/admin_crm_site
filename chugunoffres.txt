1. [P1] Сотруднику staff выдаются закрытые финансовые данные
Файлы:
  platform/api/accounts.cjs:58–59
  platform/core/store.cjs:1004–1012
  platform/core/finance.cjs:92–97, 325–331
Описание: snapshot доступен staff. Маскировка удаляет только прежние payments,
payment_links, paid/due и cost. Новый financeSnapshot безусловно добавляет expenses,
materials, certificates, passes. resources возвращается через SELECT *.
Причина: финансовые поля добавлены в общий ответ, но правила выдачи по ролям
не расширены. Скрытие раздела интерфейса не ограничивает содержимое ответа API.
Последствие: staff может получить зарплатные расходы, себестоимость материалов,
коды/остатки сертификатов, цены абонементов, pay_percent/pay_daily специалистов.
Что исправить: формировать явный разрешённый набор полей для каждой роли;
для staff исключить финансовые коллекции и ставки оплаты. Проверять отсутствие
полей в JSON, а не только отсутствие кнопок на экране.
Подтверждение: статический путь snapshot -> financeSnapshot -> reply.

2. [P1] После новой миграции ломается зачисление банковской оплаты
Файлы:
  platform/core/finance.cjs:97–100
  platform/core/store.cjs:1324–1348
Описание: financeSchema добавляет в payments шестую колонку voucher_id.
settlePaymentLink продолжает выполнять INSERT INTO payments VALUES(?,?,?,?,?).
Причина: вставка зависит от полного порядка и количества колонок таблицы.
Последствие: реальный статус success/reversed с ненулевой разницей оплаты
не записывается; обновление статуса ссылки в той же транзакции откатывается.
Что исправить: явно перечислить колонки вставки; для банковской операции
voucher_id оставить NULL. Проверить остальные INSERT без списка колонок.
Воспроизведено в памяти:
  table payments has 6 columns but 5 values were supplied

3. [P1] Резервная копия до финансовых изменений не восстанавливается
Файлы:
  platform/core/finance.cjs:90–100
  platform/core/store.cjs:1031, 1069–1083, 1102–1123
Описание: для новых таблиц есть совместимость, но нет миграции старых строк
clients/resources с отсутствующими discount, pay_percent, pay_daily.
restore перечисляет все актуальные колонки и передаёт NULL для неизвестных
старому архиву полей. Это обходит SQL DEFAULT и нарушает новые NOT NULL.
Последствие: обещанная совместимость старых копий нарушается. Восстановление
транзакционное, поэтому это отказ восстановления, а не доказанная потеря базы.
Что исправить: добавить явную миграцию формата и значения по умолчанию для новых
полей; либо вставлять только присутствующие допустимые колонки. Проверять реальную
копию, созданную предыдущим релизом, включая клиентов и специалистов.
Воспроизведено на экспорте без новых колонок:
  NOT NULL constraint failed: clients.discount

4. [P2] Ошибка валидации оставляет частично созданные/изменённые данные
Файлы:
  platform/core/store.cjs:417–448, 486–499, 873–877
  platform/core/finance.cjs:183–194, 284–289, 334–339
Описание: addClient сначала INSERT, потом setDiscount, который может выбросить
ошибку. Аналогично услуга/ресурс сохраняются до проверки материалов и ставок.
Причина: операции с несколькими связанными изменениями не обёрнуты целиком
в transaction; часть проверок выполняется после изменения базы.
Последствие: API сообщает ошибку, а запись уже существует. Повторная отправка
создаёт дубликаты; аудит и связанные настройки могут расходиться с данными.
Что исправить: сначала нормализовать и проверить входные данные, затем выполнять
все изменения и audit в одной транзакции. Для update нужна та же атомарность.
Воспроизведено в памяти: addClient({name:'Audit only',discount:101}) отвергнут,
но SELECT count(*) FROM clients после ошибки возвращает 1.

5. [P2] Общий счётчик ошибок позволяет закрыть вход всем администраторам
Файлы:
  platform/web/admin-server.cjs:14, 26–31
  platform/api/admin-auth.cjs:13
Описание: failures/resetAt в веб-сервере общие для всех посетителей. Счётчик
увеличивается до проверки формы. Пять неуспешных POST /web/login расходуют
общий лимит и вызывают 429 для остальных до сброса окна, вплоть до 15 минут.
На API дополнительный лимит по socket.remoteAddress может объединять запросы
из-за одного reverse proxy.
Условие: админка доступна извне без дополнительного ограничения доступа.
Что исправить: независимые ограниченные по размеру счётчики по доверенному IP
и учётной записи; не использовать единственную глобальную блокировку.
Origin полезен против запросов из чужого браузерного сайта, но не заменяет
защиту от клиента, который сам устанавливает HTTP-заголовки.
Подтверждение: чтение кода; запросы на блокировку production не выполнялись.

6. [P2] Общий лимит запросов API выбирает пользователя до аутентификации
Файл: platform/api/server.cjs:169–170
Описание: любой переданный Bearer превращается в ключ session:<hash> для rates
до проверки действительности сессии. Разные произвольные значения получают
разные счётчики, в том числе на публичных маршрутах.
Последствие: общий лимит 120 запросов/минуту можно обходить ротацией заголовка;
растёт число записей в Map. Это не означает обход всех отдельных лимитов endpoint.
Что исправить: для непроверенных запросов всегда применять лимит по доверенному
IP; лимит по сессии вводить только после успешной аутентификации. Ограничить
размер и время жизни Map, отдельно ограничить чувствительные публичные действия.
Подтверждение: статическое чтение, нагрузочный тест не выполнялся.

7. [P2] Новая финансовая модель ещё не согласована с отчётами и интерфейсом
Файлы:
  platform/core/finance.cjs:212–245, 252–280, 325–331
  platform/core/store.cjs:1244–1289
  platform/web/app/analytics.js:200–208
  platform/api/accounts.cjs; platform/web/app-server.cjs
Описание: в ядро уже включены продажи сертификатов/абонементов и их погашение.
Продажа хранится в certificates/passes, а погашение — в payments с методом
certificate/pass. Текущая аналитика суммирует все payments как поступления,
не учитывая отдельно продажи и неденежное погашение. Новые операции также
ещё не проведены полностью через маршруты и интерфейс.
Причина: новый модуль включён раньше завершения остальных слоёв.
Последствие при подключении новых операций: денежные поступления могут
отображаться в период погашения вместо периода продажи; неполное поведение UI.
Что исправить: явно разделить поступления денег и погашение обязательств,
обновить аналитику/права/маршруты совместно. До этого не объявлять функцию готовой.
Статус: замечание к незавершённой рабочей ветке; продажи через UI не проверялись.

К1. [P1] Тариф «за компанию» не соответствует проверке платного доступа
Файлы: platform/web/app/i18n.js:240–241;
  platform/api/accounts.cjs:21, 26, 28, 110; platform/api/server.cjs:136–137.
Описание: интерфейс обещает 499 грн/месяц или 5000 грн/год за компанию.
Подписка хранится у владельца, а дополнительные компании создаются без отдельной
покупки и без найденного лимита их количества. Все наследуют срок владельца.
Причина: бизнес, членство и оплаченный доступ разделены непоследовательно.
Последствие: одна оплата открывает все компании владельца; отдельно тарифицировать
или отключить одну компанию штатная модель не позволяет.
Исправление: выбрать тариф на аккаунт с явно указанным составом либо хранить
подписку/лимиты на business_id и проверять их при создании и использовании бизнеса.
Подтверждение: статический путь создания компании и проверки allowed().

К2. [P1] «Оферта принята» может записываться без опубликованных документов
Файлы: platform/api/legal.cjs:11–21, 31–35;
  platform/api/registration.cjs:42–44, 63, 82;
  platform/api/documents.cjs:64–80.
Описание: Legal.version возвращает 'none', если документ не найден.
record сохраняет эти версии, а accepted затем считает такую запись принятием.
Старт регистрации ради старых клиентов допускает отсутствие accept, но завершение
всё равно вызывает legal.record. Версии показанных документов в pending не сохранены:
при обновлении документа между началом регистрации и кодом запишется новая версия.
Также Legal.version не учитывает переключатель disabled, хотя публичная выдача его
учитывает: формально текущий документ может быть недоступен человеку.
Последствие: журнал принятия не гарантирует, что человек видел и принял именно этот
текст; это ослабляет доказуемость условий оплаты, обработки данных и ответственности.
Исправление: принимать только опубликованные и доступные версии; обязательное
подтверждение для новых регистраций; фиксировать показанные версии при старте,
проверять их при завершении. Старым аккаунтам показывать отдельное принятие.
Подтверждение: короткая проверка SQLite :memory: без документов дала
  offer='none', privacy='none', accepted=true, required=false.
Реальная регистрация и опубликованные документы для этого не затрагивались.

К4. [P2] Оплата подписки ручная, её подтверждение связано с настройкой почты

К5. [P2] После окончания подписки нельзя переключить компанию для экспорта
Файлы: platform/web/app-server.cjs:63, 111;

Описание: snapshot/export доступны ещё 30 дней, но переключение компании

Вход выбирает первую компанию из списка.
Последствие: владелец нескольких компаний через штатный интерфейс не может
экспортировать остальные компании в обещанный период после окончания доступа.
Исправление: разрешить чтение списка компаний и переключение в пределах readable(),
сохранив запрет на изменения. Проверить сценарий с двумя компаниями и истёкшим сроком.
Подтверждение: статический путь переключения; браузерный прогон не выполнялся.

К6. [P2] Один email не поддерживает работу в независимых компаниях
Файлы: platform/api/server.cjs:44; platform/api/accounts.cjs:21, 108.
Описание: email глобально уникален; добавление сотрудника с уже зарегистрированным
email отклоняется. У пользователя один account_id, определяющий его подписку.
Последствие: приглашение общего бухгалтера, администратора или специалиста из
другой компании требует другого email. Это ограничение для продажи сетям/подрядчикам.
Исправление: отдельно хранить личность пользователя, членства/роли и подписки
компаний; добавлять существующему пользователю membership после подтверждения.

К7. [P2] Часть обещанных сроков хранения не обеспечена найденной автоматизацией
Файлы: 33marketing/legal/privacy-site.uk.html:33–34;

К8. [P2, установка у клиента] Письма ведут на app.lomviko.com
